# AGENTS.md — uTPro Workspace Coding Standard

> Single, shared instruction file for **any AI coding agent** (Copilot, Cursor, Cline, Codex,
> Claude, Kiro, etc.) working in this workspace. Read this first. Follow it for every edit.
> When a rule here conflicts with a request, prefer the rule and flag the conflict.
>
> **Canonical source:** `uTPro.Website.Docs/AGENTS.md`. Every other copy (workspace root and each
> repo root) is generated verbatim by `uTPro.Website.Docs/sync-agents.ps1`. Edit here only, then run
> `pwsh ./sync-agents.ps1` — never hand-edit a synced copy.

Language of the codebase and all docs/comments: **English**. Chat with the maintainer may be in
Vietnamese, but everything committed (code, comments, docs, commit messages) stays English.

## 1. What this workspace is

A family of related **git repositories** under `d:\_GitHub\uTPro`, all part of the
**uTPro — Umbraco Turbo Pro** product by **T4VN**. Each folder is its own repo; treat them as
independent but stylistically identical.

| Repo (folder) | Type | Purpose |
|---|---|---|
| `uTPro/` | .NET / Umbraco solution | The main modular CMS solution (`uTPro.sln`) |
| `uTPro.Feature.*.Src/` | .NET NuGet package source | One standalone feature package each (SimpleCart, SEOAudit, FileManager, …) |
| `uTPro.Feature.*/` (no `.Src`) | Public mirror repo | Docs/README + published assets for a feature (generated by `pack.ps1`) |
| `T4VN.Seo.Core.Src/` | .NET NuGet package source | Shared SEO core library |
| `uTPro.Website.Docs/` | Jekyll site | Product documentation site (the primary docs target) + **canonical AGENTS.md** |
| `uTPro.Website.HomePage/`, `uTPro.Website.ReleaseStats/`, `T4VN.Website.HomePage/` | Jekyll / static sites | Marketing + stats sites sharing one design-token file |
| `uTPro.Sandbox.QuickStart/` | Umbraco sample | Quick-start / sandbox host |
| `store/` | Umbraco runtime | Local run data (logs, media). **Never** commit or edit generated content here. |

**Golden rule:** match the conventions already present in the file/folder you are editing. The
patterns below are extracted from the existing code — do not introduce new frameworks, libraries,
or structural patterns without being asked.

> **Multi-repo / multi-project prompts:** when the workspace opened is the parent folder
> `d:\_GitHub\uTPro`, the agent reads the **workspace-root** `AGENTS.md` and it governs the whole
> session — including a single prompt that edits files across two repos (e.g. `uTPro/` and a
> `*.Src/` package). When a single repo is opened on its own, the agent reads that repo's own
> `AGENTS.md`. Both copies are kept identical by the sync script.

## 2. .NET / C# standard (Umbraco packages & main solution)

### 2.1 Solution architecture (Umbraco Helix-inspired layers)

The main solution and feature packages follow a strict layered/modular structure. Dependencies flow
**downward only**: `Project → Feature → Foundation → Extension → Common`.

- **Common** — shared models, constants, content-type POCOs. No business logic.
- **Extension** — reusable, stateless helpers (`uTPro.Extension.*`).
- **Foundation** — infrastructure services (sitemap, robots, favicon, middleware).
- **Feature** — a discrete end-user capability.
- **Project** — the composition root / web host (`Program.cs`, `Startup/`).

Project naming: `uTPro.{Layer}.{Name}` (e.g. `uTPro.Foundation.Sitemap`,
`uTPro.Extension.CurrentSite`). Feature packages: `uTPro.Feature.{Name}`.

### 2.2 Feature-package source layout (`uTPro.Feature.{Name}.Src`)

```
uTPro.Feature.{Name}.Src/
├── src/uTPro.Feature.{Name}/       # the library (PackageId project)
│   ├── Composing/                  # IComposer + DI collection builders
│   ├── Configuration/              # Options classes bound from appsettings
│   ├── Controllers/                # Management API + public API controllers
│   ├── Migrations/                 # Umbraco NPoco migrations (cross-DB)
│   ├── Models/                     # DTOs, request/response, domain models
│   ├── Providers/                  # Pluggable strategy implementations
│   ├── Services/                   # Business logic (behind I{Name} interfaces)
│   ├── ViewComponents/ , Views/    # Server-rendered UI
│   └── wwwroot/App_Plugins/{name}/ # Backoffice UI (Lit web components)
├── src/uTPro.Feature.{Name}.TestSite/  # minimal Umbraco host for manual testing
├── tests/uTPro.Feature.{Name}.Tests/   # unit tests
├── docs/                           # getting-started.md, api.md, extensibility.md, …
├── Build/                          # pack.ps1 output (.nupkg) — do not hand-edit
├── pack.ps1                        # deterministic pack + local-cache eviction
├── README.md , LICENSE.txt , icon.png
├── umbraco-marketplace.json        # Marketplace metadata
└── uTPro.Feature.{Name}.sln
```

Add-on sub-packages live beside the core as siblings under `src/`
(e.g. `uTPro.Feature.SimpleCart.Payments.Stripe`, `.Discounts`, `.GiftCards`).

### 2.3 Dependency injection & naming

- Register services with an `IComposer`. Two accepted names, both fine — match the sibling files:
  - `{Name}Composer` (public sealed) — e.g. `SearchExtensionComposer`.
  - `DI{Name}` (internal) — e.g. `DISitemapFoundation`.
- Interface `I{Name}`, implementation `{Name}`. Keep the implementation `internal` when it is only
  consumed through its interface; the interface is `public`.
- Prefer expression-bodied `Compose` for one-liners:
  ```csharp
  public void Compose(IUmbracoBuilder builder)
      => builder.Services.AddScoped<ISitemapFoundation, SitemapFoundation>();
  ```
- Pluggable extension points are exposed as DI **collection builders** invoked from the consumer's
  own composer (no edits to the package): e.g.
  `builder.SimpleCartPaymentProviders().Append<VnPayPaymentProvider>();`.

### 2.4 C# style

- **Nullable reference types on.** Use `string?`, guard nulls, avoid `!` unless justified.
- **File-scoped namespaces** for new files (`namespace uTPro.Extension.Search;`). Older files use
  block scope — leave them unless you're already rewriting the file.
- Constructor injection into `private readonly _camelCase` fields.
- `const` / `static readonly` grouped at the top of the type.
- `sealed` classes by default unless designed for inheritance.
- Private nested helper types are `private sealed class`.
- XML `///` doc comments on **public** members. Keep them short and purpose-focused.
- Comments explain **why**, not what. Example tone from the codebase:
  `// Cache key includes the host so multi-site deployments get separate sitemaps.`
- Use Umbraco built-ins: `Constants.Conventions.*`, `IPublishedContent`, `UrlMode`,
  `IMemoryCache`, NPoco migrations (not a separate EF Core context).
- `StringComparison`/`StringComparer` must be explicit for alias/culture comparisons
  (`StringComparison.OrdinalIgnoreCase`, `StringComparison.Ordinal`).

### 2.5 Web API rules

- **Backoffice / Management API:** derive from `ManagementApiControllerBase`; route under
  `/umbraco/management/api/v1/utpro/{feature}`; **use POST** for actions to avoid the 404-redirect
  conflict; gate behind the appropriate section/policy.
- **Public / storefront API:** derive from `ControllerBase`; route under `/api/{feature}`; keep
  endpoints minimal and never trust client-supplied prices/names — resolve authoritative values
  server-side.
- Annotate with `[ProducesResponseType(...)]` and return proper status codes.

### 2.6 Packaging

- Build/pack with `pwsh ./pack.ps1` (never hand-assemble a `.nupkg`). It wipes `bin`/`obj`, packs
  every project that declares `<PackageId>`, evicts that version from the local NuGet cache, mirrors
  docs to the public repo, and restores local consumers.
- A package must **self-wire** (composer + middleware + migration + backoffice UI) so the host needs
  **no `Program.cs` changes**, and must uninstall cleanly.
- Keep `umbraco-marketplace.json` accurate (Title, Description, Tags, URLs).

### 2.7 Verify before finishing

Always build after C# changes: `dotnet build uTPro/uTPro.sln` (or the feature's `.sln`). Run tests
where they exist (`dotnet test`). Fix warnings you introduced. Do not start long-running servers
(`dotnet run`, `dotnet watch`) from an agent — tell the maintainer to run those.

## 3. Backoffice frontend (Lit web components)

Backoffice UI ships as static assets in `wwwroot/App_Plugins/{name}/` with `umbraco-package.json`.

- **Lit + ESM**, Umbraco UI Library (`uui-*`) elements. Import from
  `@umbraco-cms/backoffice/*`.
- Extend `UmbLitElement`; declare reactive `static properties`; use **private class fields**
  (`#authContext`, `#fetch()`) for internals.
- Talk to the **authenticated Management API** via the auth context — no anonymous public endpoints
  for backoffice tools.
- Keep endpoint strings in a `config.js`, HTTP helpers in `api.js`, shared styles in `styles.js`.
- Style with `uui-*` CSS custom properties and fallbacks:
  `var(--uui-color-danger, #d42054)`.
- Register with `customElements.define('utpro-{feature}-{view}', ClassName)` and export default.
- Localize backoffice strings via `App_Plugins .../lang/*.js`.

## 4. Site frontend (main web project & Jekyll sites)

### 4.1 CSS / SCSS design tokens — single source of truth

All colors, fonts, radii, shadows and layout metrics are **CSS custom properties** defined once in a
`_variables.scss` (or `variables.css`) file. **Never hard-code a hex/size that a token exists for** —
use `var(--token-name)`.

The token file is shared **verbatim** across `uTPro.Website.HomePage` (canonical),
`uTPro.Website.Docs`, and `uTPro.Website.ReleaseStats`. If you must change a token:

1. Edit the canonical file in `uTPro.Website.HomePage/scss/_variables.scss`.
2. Copy it verbatim to the other sites (there is a `sync-tokens.ps1`).
3. **Never rename or remove** a token another site consumes — token names are the contract. Add new
   ones with a `--name: value;` line.

### 4.2 Main web project CSS convention (`uTPro.Project.Web/wwwroot/css/{SiteName}/`)

- `variables.css` = design tokens; `critical.css` = inlined above-the-fold; `layout.css`,
  `main.css`, `navHeader.css`, etc. for the rest.
- Per-component CSS in `Components/{ComponentName}.css`, loaded on demand via
  `Html.SetSection(...)` so unused CSS never ships.
- **JavaScript from components uses the Script Queue** (`Html.QueueScript` /
  `QueueStandaloneScript`), not raw `<script>` tags.
- Multi-site theming: each site's folder is named after `CurrentSite.GetItem().Root.Name`.

### 4.3 Jekyll sites

- Structure: `_config.yml`, `_data/*.yml`, `_includes/`, `_layouts/`, `_sass/`, `assets/`.
- `_site/` and `.jekyll-cache/` are **build output** — never edit or commit intentionally.
- Vanilla JS in `assets/js/` (e.g. `lightbox.js`), SCSS partials in `_sass/` imported by one entry
  stylesheet. Keep JS dependency-free unless a library is already in use.

## 5. Documentation standard (emphasis)

Docs are a first-class deliverable. When you add or change a feature, update its docs in the same
change. There are three doc surfaces — use the matching format.

### 5.1 Jekyll docs site (`uTPro.Website.Docs/docs/`)

- File naming: `N.-Title-With-Hyphens.md` where `N` is the ordinal (`3.-Project-Structure.md`).
- **Every page starts with YAML front matter:**
  ```yaml
  ---
  layout: default
  title: "Project Structure"
  description: "One-sentence SEO description of the page."
  permalink: "/3-Project-Structure/"
  nav_order: 5
  ---
  ```
- First heading `# N. Title`, then an **audience callout**:
  `> For: **Developer** — one line on what this page covers.`
- Use `## N.N` numbered sub-sections matching the page number.
- Cross-link with permalinks and anchors: `[4. Configurations](/4-Configurations/#48-database-provider)`.
- Prefer **tables** for reference material (members, parameters, routes), fenced code blocks with a
  language tag (` ```csharp `, ` ```razor `, ` ```json `, ` ```bash `), and blockquote `>` for
  notes/warnings/important callouts. Use the ⭐ emoji sparingly to mark the one thing that matters
  most in a list.

### 5.2 Feature-package docs (`{Feature}.Src/docs/*.md`)

- Lowercase-hyphen names: `getting-started.md`, `api.md`, `extensibility.md`, `orders.md`.
- `getting-started.md` follows numbered steps: **Install → First boot → Create/Configure →
  Render/Use**, with copy-paste `dotnet add package …`, `appsettings` JSON, and `.cshtml`/`.js`
  snippets.
- Document APIs as a method/route/body/result **table** (see SimpleCart README/api.md).
- These are mirrored to the public feature repo by `pack.ps1` — write them for external consumers.

### 5.3 README / CONTRIBUTING (per repo)

- README opens with a one-paragraph "what & why", then **Install**, feature sections, **Security**,
  **Building/packing**, **Test site**, **License**. Keep the confident, concise, benefit-first tone
  already used (e.g. SimpleCart README).
- CONTRIBUTING lists the fork→branch→build→commit→PR flow and the project conventions. Reference the
  build command `dotnet build uTPro/uTPro.sln`.

### 5.4 Documentation writing style

- Second person, present tense, active voice. Concise sentences; no filler or hype.
- Show, don't tell — lead with a working snippet, then explain the parameters.
- State the **why** behind a default or constraint (e.g. "prices resolve server-side so they can't
  be spoofed").
- Keep terminology consistent with the code (same alias/option/interface names).
- Update the relevant doc page **in the same PR** as the code change; never let docs drift.

## 6. Git & commits

- Branch per change: `feature/…` or `fix/…`. Do not commit to `main`/`master` directly.
- Commit messages: short imperative prefix used in this org — `Add: …`, `Fix: …`, `Update: …`.
- **Only commit when the maintainer asks.** Stage specific files, not `git add .`.
- Never commit build output (`bin/`, `obj/`, `_site/`, `.jekyll-cache/`, `Build/*.nupkg` beyond what
  is intended), local run data under `store/`, secrets, or `.env`-style files. Respect each repo's
  `.gitignore`.
- Flag any file that may contain secrets before staging it.

## 7. Quick checklist before you finish a task

- [ ] Matched the conventions of the surrounding files (naming, namespace style, DI pattern).
- [ ] Used design tokens / Umbraco built-ins instead of hard-coded values.
- [ ] Built the affected solution and ran available tests; fixed introduced warnings.
- [ ] Updated the matching docs (Jekyll page, feature `docs/`, and/or README) in the same change.
- [ ] No secrets, build output, or `store/` runtime data committed.
- [ ] Did not start long-running servers from the agent.
